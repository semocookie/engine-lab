## 실험 1 — 복사는 어디서 생기나

`Payload` 는 64자짜리 `std::string` 을 들고 있다. 복사가 일어나면 힙 할당까지 따라온다.

| 코드 | 예측 복사 | 실측 복사 | 비고 |
|---|---:|---:|---|
| `TakeByValue(a)` | 1 | 1 | |
| `TakeByConstRef(a)` | 0 | 0 | |
| `Payload b = a;` | 1 | 1 | |
| `b = a;` (이미 있는 객체에 대입) | 0 | 1 | 그냥 값만 복사되는 형태라고 생각했는데 operator=이 호출된다. |
| `v.push_back(a)` | 1 | 1 | |
| `v.push_back(Payload(3))` — 임시 | 1 | 1 | |
| `v.emplace_back(4)` | 0 | 0 | |

- `push_back(임시)` 와 `emplace_back` 이 갈린 이유:
  push_back은 과정 중에 임시 Payload를 생성해 복사 생성을 하고 삭제하는 식으로 vector 내부를 채우고 emplace_back은 받은 인자를 바로 생성자에 전달해 생성하는 방식이다.

## 실험 2 — `std::move` 는 무엇을 옮기는가

| 항목 | 예측 | 실측 | 비고 |
|---|---|---|---|
| `Payload b = std::move(a);` 의 복사 횟수 | 0 | 1 | std::move로 복사 생성이 안될 거라고 생각했음. 실제론 하고 있음. |
| 옮긴 뒤 `a.Data` 의 길이 | 64 | 64 | |

- `std::move` 라는 이름을 보고 무엇을 기대했는가. 실제로 이 함수가 하는 일은:
  a에 대한 소유권을 b에게 move하는 것이라고 생각했다. 실제는 a를 우측값으로 바꾸고 이동 생성자를 찾아보니 정의된 이동 생성자가 없어서 복사 생성을 했다.

- 그럼 **무엇이 있어야** 실제로 옮겨지는가:
  Payload에 이동 생성자를 정의해야된다.

## 실험 3 — 반환할 때는 몇 번 복사되는가

### 3-a. 반환하는 식의 값 범주

식(expression)은 성질 두 개로 갈린다 — **신원**(가리키는 객체가 있나)과 **이동 가능**(훔쳐가도 되나).

| 식 | 예측 | 실측 |
|---|---|---|
| `Payload(1)` | prvalue | prvalue |
| `p` (지역 변수) | lvalue | lvalue |
| `std::move(p)` | xvalue | xvalue |

### 3-b. 각각을 반환하면

| 코드 | 값 범주 | 예측 복사 | 실측 (복사 / 이동) | 비고 |
|---|---|---:|---|---|
| `return Payload(1);` | prvalue | 1 | 0 / 0 | |
| `Payload p; return p;` | lvalue | 2 | 0 / 0 | |
| `return std::move(p);` | xvalue | 1 | 1 / 0 | |

- 비고 : NRVO는 반환 변수를 하나로 확정할 수 있을 때만 걸린다.

- 값으로 반환했는데 앞의 두 줄이 0인 이유:
  함수 안 생성자의 this와 바깥 x의 주소가 같았다. 애초에 x 자리에 지어졌기 때문에 옮기거나 베낄 일이 없었다. 이걸 복사 생략(RVO)이라 하고 prvalue를 반환하는 경우는 C++17부터 보장된다.

- 세 번째 줄만 결과가 다르다면, 값 범주 표의 어느 성질 때문인가:
  std::move(p)는 xvalue라 신원이 있다. 이미 존재하는 객체를 가리키니 "목적지에서 만들면 그만"이 성립하지 않고, 그 객체에서 옮기거나 베껴야 한다. prvalue만 신원이 없어서 생략이 가능하다.

## 실험 4 — `auto` 가 만드는 복사

| 코드 | 예측 복사 | 실측 복사 | 비고 |
|---|---:|---:|---|
| `auto p = GetConstRef();` | 1 | 1 | |
| `const auto& p = GetConstRef();` | 0 | 0 | |
| `for (auto e : v)` — 원소 3개 | 3 | 3 | |
| `for (const auto& e : v)` — 원소 3개 | 0 | 0 | |

- 비고 : Payload 는 64자 문자열을 들고 있으니 복사 3회 = 힙 할당 3회입니다. 원소의 갯수에 따라 횟수가 더해집니다. const auto& 하나로 0이 되는 게 이 실험의 결론입니다.

- `auto` 가 무엇을 떼어내기 때문에 이렇게 되는가:
  const와 레퍼런스(&)를 떼어냅니다.

## 실험 5 — 람다 캡처

| 캡처 | 예측 복사 | 실측 복사 | 예측 sizeof | 실측 sizeof |
|---|---:|---:|---:|---:|
| `[a]` 값 캡처 | 1 | 1 | 76 | 40 |
| `[&a]` 참조 캡처 | 0 | 0 | 8 | 8 |
| `[b]` → **TODO 3 후** `[b = std::move(b)]` | 0 | 1 | — | — |

- 비고
  - **`[a]` 의 sizeof 를 76 으로 봤다.** 64자 문자열이 통째로 들어갈 줄 알았는데, `std::string` 객체는 힙 주소·길이·용량만 들고 **32바이트**다. 내용은 힙에 있다. `32 + 4 + 패딩 4 = 40`.
  - **`std::move` 를 쓰면 옮겨질 줄 알았다 — 실험 2에 이어 두 번째다.** `Payload` 에 이동 생성자가 없어 우측값이 `const&` 로 떨어졌고 결국 복사였다. TODO 3 만으로는 안 바뀌고 **TODO 1 이 있어야** 이 줄이 이동 1 이 된다.
  - [b = std::move(b)] - TODO 1 까지 하고 나서야 이동 1 이 됐다.

- 람다의 `sizeof` 를 정하는 것은 무엇인가:
  값 캡처는 복사된 객체의 크기(std::string 32 + int 4 + 패딩 4 = 40)로 정해지고, 참조 캡처는 `a` 를 가리키는 포인터 하나라 8바이트로 정해진다.

## 실험 6 — `vector` 가 자리를 늘릴 때

`reserve(2)` 로 꽉 채운 뒤 하나 더 넣는다. 기존 원소 2개가 어떻게 되는가.

| 시점 | 예측 (복사 / 이동) | 실측 (복사 / 이동) | 비고 |
|---|---|---|---|
| TODO 1 **전** (이동 생성자 없음) | 2 / 0 | 2 / 0 | |
| TODO 1 **후** (이동 생성자 있음, `noexcept` 없음) | 0 / 2 | 2 / 0 | |
| TODO 2 **후** (`noexcept` 붙임) | 0 / 2 | 0 / 2 | |

- TODO 1 만으로는 바뀌지 않았다면, `vector` 는 무엇을 보고 판단한 것인가:
  noexcept를 보고 판단하고 있다.

- 왜 그렇게 판단하도록 만들어졌는가 (재할당 도중에 예외가 나면 어떻게 되는가):
  재할당 중 예외가 나오면 다시 원본은 그대로 두고 재할당 하던 vector만 삭제하면 되는데 이동은 원본 자체의 연결을 끊어버리기 때문에 불가능하다.

## 실험 7 (덤) — 정적 바인딩과 동적 바인딩

`Child` 를 만들어 `Base*` 로 넘겼다.

| 호출 | 예측 출력 | 실측 출력 | 비고 |
|---|---|---|---|
| `p->Plain()` (`virtual` 없음) | Base::Plain | Base::Plain | |
| `p->Virt()` (`virtual` 있음) | Child::Virt | Child::Virt | |
| `sizeof(Base)` | 1byte | 8byte | 1byte는 가상 함수조차 없을 때를 나타내고 vptr이 생겨 8byte가 된다. |

어셈블리로 확인한다. 두 `call` 이 어떻게 다른가.

```
cl /nologo /EHsc /O2 /std:c++20 /FAsc /c main.cpp
```

`main.cod` 에서 `CallBoth` 를 찾아 붙여넣는다:

```asm
CallBoth:
  ...
  lea  rcx, "Base::Plain\n"
  call printf                        ← p->Plain() 이 통째로 인라인됐다

  ...
  mov  rax, QWORD PTR [rbx]          ← vptr 을 읽는다
  mov  rcx, rbx                      ← this
  rex_jmp QWORD PTR [rax]            ← 그 표에 적힌 곳으로 간접 점프
```

- 두 호출의 차이를 한 줄로:
  정적 바인딩은 컴파일 단계 때 인라인화 혹은 바로 그 주소로 호출되도록 하지만 동적 바인딩은 vptr을 통해 실제 객체의 클래스의 동작을 호출한다.
