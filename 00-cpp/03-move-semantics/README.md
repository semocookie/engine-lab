## 어떻게 동작하나

- lvalue를 rvalue로 바꾸는 함수이다. 실제로 lvalue에 더블 레퍼런스(&&)를 붙여 rvalue로 바꿀 뿐이고, 받는 쪽이 객체를 생성할 때만 이동 생성자를 사용한다. 
- std::move(a)는 a에 &&를 붙일 뿐이고 인자가 const &&, &&, const & 일 때 호출이 가능하다. 클래스에 복사 생성자, 복사 대입, 소멸자 중 하나라도 직접 선언하면 이동 생성자를 자동으로 생성해주지 않습니다. 이동 생성자가 없는 경우는 const &&, &&가 없는 경우이며 그 다음 가능한 const &로 호출된다. 의도가 이동 생성이라면 const &로 받을 경우 별다른 오류없이 정상 작동하기 때문에 조심해야한다.
- 값으로 반환한다고 복사가 나는 것은 아니다. 호출자가 결과를 놓을 자리의 주소를 숨은 인자로 먼저 넘기고, 함수는 그 자리에 객체를 직접 짓는다. 그래서 return 은 값을 들고 나오는 것이 아니라 받은 자리를 채웠다는 뜻이고, 실제로 함수 안의 this 와 바깥 변수의 주소가 같았다. 이름 없는 것을 그대로 반환하는 경우를 RVO 라 하며 C++17 부터 반드시 그렇게 하게 되어 있다. 이름 있는 지역 변수를 반환하는 경우는 NRVO 라 하며 컴파일러 재량이라 조건이 붙는다 — try-catch 안이거나 경로마다 반환하는 변수가 다르면 깨졌고, return std::move(p) 처럼 도우려고 붙인 것이 오히려 막았다.
- auto를 사용할 경우 반환값이 const와 레퍼런스(&)가 제거된 형태이다. 레퍼런스를 제거된 형태로 받게 되면 복사 생성이 되기 때문에 레퍼런스로 원본을 받아 복사하지 않게 한다.
- 람다는 컴파일러가 만드는 이름 없는 클래스다. 캡처는 어떤 변수들을 멤버 변수로 받아올 것인가에 대한 설정이다. 값으로 받으면 일반 변수로 복사하고 참조로 넣으면 주소를 받아오게 되고 std::move를 넣으면 이동 생성을 통해 소유권을 받아오게된다. 결국 이름 없는 클래스의 크기도 캡처에 의해 달라진다. 값이나 이동으로 받으면 값의 크기로 바뀌고 참조로 받으면 주소를 받기 때문에 포인터 크기 8byte 만큼 생긴다. 참조의 경우 주소만 받아와 후에 읽기 때문에 캡처를 사용할 때 댕글링 포인터를 조심해야 한다.
- 재할당 시 noexcept의 유무에 따라서 이동과 복사를 선택하도록 했다. 왜냐하면 중간 예외를 통해 재할당을 실패할 시 원본을 복원해야 되는데 이동을 하게 될 경우 앞에 이동 생성을 한 것들이 복원되지 않기 때문이다.
- 정적 바인딩은 컴파일 단계 때 호출 주소가 어디인지 기계어에 바로 적혀 호출되고 동적 바인딩은 런타임에 vptr을 거쳐 호출될 주소를 결정한다.

## ⚠️ 틀렸던 것

### 두 번 걸린 것

**`std::move` 가 무언가를 옮긴다고 알고 있었다.**
`std::move` 는 `<type_traits>` 의 `static_cast<remove_reference_t<_Ty>&&>` 한 줄이 전부다. 옮기는 일은 받는 쪽 이동 생성자가 한다. 이동 생성자가 없는 상태에서 `Payload b = std::move(a);` 를 했더니 **복사 1** 이 세어졌고 `a.Data` 는 64자 그대로였다. 오류도 경고도 없었다. 어제 예측에서 한 번 틀렸고, 다음 날 문서를 쓰면서 "이동 생성자가 복사 생성자로 대체된다" 고 또 썼다.

**`const auto&` 가 이동을 시킨다고 알고 있었다.**
실측은 **복사 0 · 이동 0**. 아무것도 만들지 않는다. 그리고 복사를 만든 것은 `range-for` 가 아니라 **원소를 받는 선언을 값으로 썼다는 사실** 이다. `for (auto e : v)` 3, `for (const auto& e : v)` 0, 반복문 밖에서 `auto p = GetConstRef()` 도 1 이었다.

### 자료를 덮고 꺼낼 때 틀린 것

**반환형과 실제로 뽑히는 오버로드를 같은 것으로 봤다.**
후보에 `Payload&&` 가 없는 상황에서도 `Payload&&` 가 뽑힐 거라고 답했다. 없는 것이 뽑힐 수는 없다. 반환형은 `Payload&&` 하나로 고정이고, 그 식이 **어느 자리로 들어가느냐** 는 별개 문제다. `Payload&&` 자리가 없으면 `const Payload&&`, 그것도 없으면 `const Payload&` 로 한 칸씩 밀려 내려간다. **대체가 아니라 낙하다.**

**참조 바인딩에서 `T&` 가 넓고 `const T&` 가 좁다고 봤다.**
20칸을 채워 12개만 맞았고, 틀린 8칸이 전부 그 두 열이었다. `T&` 열 다섯 칸을 모두 `O` 로 적었는데 실제로는 맨 위 하나만 `O` 다.

| 인자 \ 매개변수 | `T&` | `const T&` | `T&&` | `const T&&` |
|---|:--:|:--:|:--:|:--:|
| `a` (비-const 좌측값) | O | O | X | X |
| `ca` (const 좌측값) | X | O | X | X |
| `std::move(a)` | X | O | O | O |
| `std::move(ca)` | X | O | X | O |
| `Payload(9)` (임시) | X | O | O | O |

`Payload& c = std::move(a);` 는 아예 컴파일이 안 된다.
`error C2440` — *비const 참조는 lvalue에만 바인딩할 수 있습니다.*

**`const T&` 만 열 전체가 `O` 라는 이 한 칸의 예외가 이 주제 전체를 만든다.** 이동할 자리가 없으면 전부 여기로 떨어지고, 문이 열려 있으니 오류도 경고도 나지 않는다.

**참조를 만드는 것이 소유권을 넘기는 일이라고 봤다.**
`Payload&& r = std::move(a);` 에서 이동 1 이 세어지고 `a` 가 빌 거라고 예측했다. 실측은 **복사 0 · 이동 0**, `a.Data` 는 64자 그대로, 그리고

```
&a = 0000002BE5B8FA30
&r = 0000002BE5B8FA30
```

**같은 주소다.** 객체는 하나고 이름표만 늘었다. 참조를 만들 때는 생성자가 호출되지 않는다.
왼쪽에 `&` 나 `&&` 가 있으면 이름표, 없으면 새 상자다. 이동이냐 복사냐가 갈리는 것은 **새 상자를 만들 때뿐** 이다.

그래서 `T&&` 로 받은 매개변수도 **이름이 있으므로 lvalue** 이고, 안에서 다시 `std::move` 를 걸지 않으면 복사(1/0)가 된다. 어제 이동 생성자에 `Data(std::move(Other.Data))` 라고 쓴 이유가 이것이었는데, 그때는 이유를 모르고 썼다.

**이동 캡처가 참조처럼 주소만 든다고 봤다.**
실측은 **40바이트**, 값 캡처와 같다. 8바이트인 것은 참조 캡처뿐이다.

| 캡처 | 멤버 타입 | `sizeof` |
|---|---|--:|
| `[a]` | `Payload` | 40 |
| `[b = std::move(b)]` | `Payload` | 40 |
| `[&a]` | `Payload&` | 8 |

크기를 정하는 것은 **람다 안에 무엇을 두느냐**(실물이냐 주소냐)이고, 복사냐 이동이냐는 **그 실물을 어떻게 채우느냐**의 문제다. 두 축을 하나로 봤다.

### 실험 예측에서 틀린 것

**이동 생성자만 만들면 `vector` 가 이동할 줄 알았다.**
만든 뒤에도 **2/0** 이었고, `noexcept` 한 단어를 붙이자 **0/2** 가 됐다. `<vector>` 838행이 `is_nothrow_move_constructible_v<_Ty> || !is_copy_constructible_v<_Ty>` 를 본다. 이동 생성자가 **있는지** 가 아니라 **`noexcept` 로 선언됐는지** 를 보는 것이고, 이유는 재할당의 **강한 예외 보장** 이다. 옮기는 도중 예외가 나면 새 메모리만 버리면 되는데, 이동이었다면 원본이 이미 비어 있어 되돌릴 것이 없다.

**그 밖에** — `b = a` 대입에서 복사 0 을 예측했으나 1 이었고, 람다 크기를 76 으로 예측했으나 40 이었으며(`sizeof(std::string)` 을 64 를 품은 크기로 봤다), 순수 가상 함수 호출이 크래시로 이어지는 경로를 확인하지 않은 채 예측했다.

## 언리얼과의 연결

- 확인 했을 때는 명시적으로 static_cast를 해주지 않은 것 빼고는 같았다. 다만 lvalue가 아니거나 const가 있으면 assert를 발생시킨다. const & 일 때 오류없이 넘어가던 문제를 엄격하게 막은 버전이 MoveTemp, 기존 std::move와 같은 버전이 MoveTempIfPossible로 존재.
- 현재 가지고 있는 메모리 블록 자체를 늘려달라고 realloc으로 맡기고 복사, 이동, 생성자 호출 등을 하지 않는다.
- const &를 붙여서 넘기고 있다.
- 람다 자체는 그냥 보관하고 있다가 첫번째 파라미터로 받은 포인터가 죽으면 실행하지 않는다.
