# 객체 메모리 레이아웃

---

## 한 줄

구조체와 클래스의 크기는 단순히 멤버 변수 크기의 합이 아니라 멤버 변수의 정렬 규칙에 의해 결정된다. 멤버 변수의 순서만 변경해서 48바이트에서 32바이트로 줄일 수 있다.

<!-- 이 주제를 한 문장으로. 예: "구조체 크기는 멤버 합이 아니라 정렬 규칙이 정한다." -->

## 어떻게 동작하나

- 타입마다 alignof가 있고, 그 타입의 객체는 주소가 alignof의 배수인 자리에만 앉을 수 있다. 구조체와 클래스의 전체 크기는 멤버 변수 중 제일 큰 alignof 크기 배수이다.
- 제일 큰 alignof 크기보다 작은 alignof를 가진 멤버 변수들은 자신의 alignof 크기 배수의 공간부터 할당 되고 그 사이 나머지 공간들은 패딩 바이트로 채운다. 만약 마지막 멤버 변수가 전체를 채우지 못하더라도 제일 큰 alignof의 배수가 될 때까지 패딩 바이트로 채운다.
- 배열의 원소는 sizeof 간격으로 놓이므로, sizeof가 alignof의 배수가 아니면 둘째 원소부터 정렬이 깨진다. 그러므로 정렬을 위해 전체를 alignof 배수에 맞춘다.
- 만약 alignof의 배수가 아니라면 메모리와 캐시 사이의 데이터를 보내는 단위인 캐시 라인을 걸쳐서 저장되는 경우가 생길 수 있으므로 데이터가 항상 일정한 공간에 정렬되도록 alignof의 배수로 설정된다. 
- 가상 함수를 포함한 클래스의 경우에는 그 vtable이 객체마다가 아니라 클래스마다 하나 생성되고, 그 v 가리키는 vptr이 생성 되는데 주소상 멤버 변수 중 가장 앞에 배치된다.(포인터는 32비트 환경은 4바이트, 64비트 환경은 8바이트 크기를 가진다.)

## ⚠️ 틀렸던 것

- short의 기본 자료형을 1바이트로 잘못 알고 있었음. 실제로는 2바이트.
- 실험 3에서 Poly 구조체 마지막 계산 후 패딩 바이트를 넣어 최대 alignof 배수에 맞추는 과정을 누락. vptr의 alignof 8바이트에 맞춰서 전체를 8의 배수인 16으로 맞추기 위해 4바이트 패딩이 붙는다.
- 실험 3에서 마지막 패딩 바이트 누락과 vptr을 두개로 잘못 계산. PolyChild의 vptr 하나만 계산해서 8 + 4 + 4(패딩 바이트)로 Poly와 똑같은 크기로 예측 했어야 됐는데 8 + 8 + 4로 계산.
- 슬라이싱에서 레퍼런스로 함수 호출 시 결과 예측 오해. 처음에는 Poly& ref = c; 에서 선언 타입이 Poly니까 Poly::speak가 나올 거라 예측했는데 PolyChild::speak였다. 참조는 새 객체를 만들지 않으니 c의 vptr을 그대로 따라간다.

## 언리얼과의 연결

- UE5의 FVector는 double 3개로 24byte. FVector4는 double 4개로 32byte.
  SIMD 로 다루려면 주소가 16의 배수여야 하므로, FVector4·FQuat·FMatrix 는
  MS_ALIGN(16) 으로 정렬을 명시적으로 요구한다. → 실제 alignof 확인 필요 `?`
- 액터가 1000개일 때 객체당 8바이트를 아끼면 8000byte == 약 7.8kb 이다. 
- 네트워크에서 패킷을 보낼 때 발신과 수신 쪽 플랫폼의 차이에 의해 패킷 해석이 달라질 수 있다. 언리얼은 수신, 발신 쪽 정렬 규칙을 맞추는 대신 신경쓰지 않도록 설계되어 있다. 예를 들어 메모리를 통째로 복사하지 않고 값을 하나씩 골라 적어 보내는 명시적 직렬화를 통해 메모리 배치와 무관해진다.
- 64바이트 캐시 라인 기준으로 만약에 군데군데 패딩 바이트 들어간 48바이트 구조체와 멤버 순서를 정렬해 32바이트로 줄인 구조체를 봤을 때 48바이트의 구조체는 1.33개를 읽을 수 있지만 32바이트 구조체는 2개를 읽을 수 있다.
