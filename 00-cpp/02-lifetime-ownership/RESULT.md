## 실험 1 — 생성과 소멸의 순서

`Car : Vehicle` 이고, `Car` 안에 멤버 `Engine` 이 있다.
아래 여섯 줄이 **몇 번째로 출력될지** 1~6을 적는다. (행 순서는 일부러 섞어두었다)

| 출력되는 줄 | 예측 순서 | 실측 순서 | 비고 |
|---|---:|---:|---|
| `- Engine (멤버)` | 4 | 5 |  |
| `+ Car (파생)` | 2 | 3 |  |
| `- Vehicle (기반)` | 6 | 6 |  |
| `+ Engine (멤버)` | 3 | 2 |  |
| `- Car (파생)` | 5 | 4 |  |
| `+ Vehicle (기반)` | 1 | 1 |  |

- 생성 순서가 그렇게 되는 이유:
  가장 먼저 부모 클래스의 생성부터 되고 그 다음 멤버 변수 생성 후에 생성자가 호출되는 순서이다. 생성자에서도 멤버 변수에 접근할 수 있기 때문에 멤버 변수 생성 전에 생성자가 호출이 되면 문제가 된다.
- 소멸이 생성의 **역순**인 이유:
  만약 소멸할 때 멤버 변수 데이터부터 없어진다고 하면 소멸자일 때 먼저 없어진 데이터에 접근하기 때문에 멤버 변수 생성 -> 생성자 호출 -> 소멸자 호출 -> 멤버 변수 제거 순으로 해야 문제가 없다.

## 실험 2 — 생성자·소멸자 안의 가상 함수

`Pawn : Actor` 이고 `Pawn` 이 `WhoAmI()` 를 재정의했다.

| 부른 위치 | 예측 출력 | 실측 출력 | 비고 |
|---|---|---|---|
| `Actor` 생성자 안 | Actor::WhoAmI | Actor::WhoAmI |  |
| 다 만들어진 뒤 | Pawn::WhoAmI | Pawn::WhoAmI |  |
| `Actor` 소멸자 안 | Actor::WhoAmI | Actor::WhoAmI |  |

- 이렇게 되는 이유를 **vptr** 로 설명하면 (주제 1에서 본 그것):
  생성자 호출 시 vptr에 vtable 주소를 저장한다. 그러므로 아직 Pawn의 생성자가 호출되지 않은 시점의 Actor 생성자 안에서는 Actor의 vtable의 주소가 vptr에 있으므로 Actor::WhoAmI가 호출된다. 다 만들어진 뒤의 Pawn의 생성자까지 호출된 뒤이므로 Pawn의 vtable로 연결되고 Actor의 소멸자가 호출되면서 Actor의 vtable 주소가 vptr에 있으므로 Actor::WhoAmI가 호출된다.
- 그래서 생성자·소멸자에서 가상 함수를 부르면 안 되는 이유:
  생성자, 소멸자 단계에서는 순서 상 가상 함수를 호출해도 호출된 클래스에서 정의된 함수만 호출될 수밖에 없다. 만약에 순수 가상 함수를 생성자나 소멸자에서 호출하게 되면 크래시가 발생한다.

## 실험 3 — 가상 소멸자

기반 클래스 포인터로 받아서 `delete` 했을 때 **어떤 소멸자들이 불렸는가.**

| | 예측 | 실측 | 비고 |
|---|---|---|---|
| `NoVirtual~` (virtual 없음) | + NoVirtualChild 가 쥔 자원<br>- NoVirtualBase<br>- NoVirtualChild 가 쥔 자원 | + NoVirtualChild 가 쥔 자원<br>- NoVirtualBase<br> |  |
| `Virtual~` (TODO 3 **전**) | + VirtualChild 가 쥔 자원<br>- VirtualBase<br>- VirtualChild 가 쥔 자원 | + VirtualChild 가 쥔 자원<br>- VirtualBase<br> |  |
| `Virtual~` (TODO 3 **후**) | + VirtualChild 가 쥔 자원<br>- VirtualChild<br>- VirtualBase<br>- VirtualChild 가 쥔 자원 | + VirtualChild 가 쥔 자원<br>- VirtualChild<br>- VirtualChild 가 쥔 자원<br>- VirtualBase<br> |  |

- `virtual` 이 없을 때 무엇이 불리지 않았는가:
  파생 클래스의 소멸자가 호출되지 않았다.
- 그래서 생긴 문제는:
  소멸자가 호출되지 않고 멤버 변수가 정리되지 않았다. 특히 파생 클래스 소멸자 부분에서 객체 delete 등을 호출하면 소멸자가 호출되지 못해 정리되지 못해 메모리 누수가 생길 수 있다.
- **모든 클래스에 virtual 소멸자를 붙이면 되지 않나?** 안 그러는 이유:
  파생 클래스를 이용해 업캐스팅을 해서 delete 할 경우가 있으면 붙여야겠지만 자기 타입 그대로 쓸 경우 오히려 붙이면 가상 함수가 포함된 클래스가 되어 vptr 8바이트만 불필요하게 포함되어 공간만 낭비된다.

## 실험 4 — 중간에 빠져나갈 때

두 함수 모두 예외로 중단시켰다. 소멸(`-`) 줄이 찍히는가?

| 함수 | 예측 | 실측 | 비고 |
|---|---|---|---|
| `ManualDelete` | + ManualDelete 가 만든 것<br>중간에 실패<br>(예외 잡음) | + ManualDelete 가 만든 것<br>(예외 잡음) | 처음엔 `중간에 실패` 도 찍힐 줄 알았다. 예외 메시지는 `catch` 에서 `e.what()` 을 꺼내야 나온다 |
| `RaiiVersion` (TODO 1 **전**) | + RaiiVersion 이 만든 것<br>(예외 잡음) | + RaiiVersion 이 만든 것<br>(예외 잡음) |  |
| `RaiiVersion` (TODO 1 **후**) | + RaiiVersion 이 만든 것<br>- RaiiVersion 이 만든 것<br>(예외 잡음) | + RaiiVersion 이 만든 것<br>- RaiiVersion 이 만든 것<br>(예외 잡음) | `-` 가 `(예외 잡음)` 보다 **먼저** 나온다 — 스택 되감기 |

- `ManualDelete` 에서 `delete` 를 지나치게 되는 경로가 몇 가지나 되는가 — 지금 코드 기준으로, 그리고 이 함수를 앞으로 고쳐 나간다면:
  bFail이 true일 때 throw를 호출해 강제적으로 함수 밖으로 나가기 때문에 delete를 지나치는 경우는 하나밖에 없다. 이후에 고쳐 나간다면 delete 사이에 return을 사용해 함수를 빠져나오는 경우 같은 일들이 무수히 발생할 수 있다.
- **RAII 한 줄 정의:**
  소멸자를 가진 객체 예를 들어 스마트 포인터 등을 이용해서 자원인 객체를 소유하게 만들어서, 스코프를 나갈 때 지역 변수로 생성한 스마트 포인터가 스코프를 빠져나감과 동시에 소멸자를 호출할 때 자연스럽게 객체의 delete도 같이 호출해 같이 해제하는 방법.

## 실험 5 — 스마트 포인터

| 타입 | 예측 sizeof | 실측 sizeof | 비고 |
|---|---:|---:|---|
| `int*` | 8byte | 8byte |  |
| `std::unique_ptr<int>` | 8byte | 8byte |  |
| `std::shared_ptr<int>` | 8byte | 16byte | `unique_ptr` 과 똑같이 8byte 로 봤다. 스마트 포인터는 다 포인터 하나 크기라고 뭉뚱그려 알고 있었던 것. 실제로는 8byte 짜리가 하나 더 붙어 있다 |

- `unique_ptr` 이 생포인터와 같은 크기인 이유 (주제 1의 **EBO**):
  unique_ptr 클래스 안에 주소 저장을 위한 포인터와 삭제자 공간이 있는데 삭제자에 빈 공간의 클래스가 있으면 EBO가 걸려 0byte로 되고 포인터를 위한 공간만 걸려 8byte 크기가 된다.
- `shared_ptr` 이 더 큰 이유 — **무엇을 하나 더 들고 있는가**:
  내부를 살펴보니 포인터 저장을 위한 element_type* _Ptr과 레퍼런스 카운터를 저장하는 base _Ref_count_base* _Rep를 두 개 들고 있다. _Rep 안에 _Uses를 레퍼런스 카운터로 쓰고 있고 이게 0이 되어야 갖고 있던 객체를 삭제한다.

### 소유권 이전

| | 예측 | 실측 | 비고 |
|---|---|---|---|
| `std::move` 후 `a` 의 상태 | nullptr | 비었음 |  |
| `auto c = b;` 주석을 풀면 | 컴파일 에러 | 컴파일 에러(E1776 참조할 수 없습니다. 삭제된 함수입니다.) |  |

컴파일 에러 메시지에서 핵심 한 줄:
```
error C2280: 'unique_ptr(const unique_ptr&)': 삭제된 함수를 참조하려고 합니다.
```

### 참조 카운트

| 시점 | 예측 `use_count` | 실측 | 비고 |
|---|---:|---:|---|
| `s1` 만든 직후 | 1 | 1 |  |
| `s2` 로 복사한 뒤 | 2 | 2 |  |
| `s2` 가 사라진 뒤 | 1 | 1 |  |

## 실험 6 — 순환 참조

`A->Next = B`, `B->Prev = A` 로 서로를 가리키게 했다.

| | 예측 | 실측 | 비고 |
|---|---|---|---|
| 연결 후 `A.use_count` | 2 | 2 |  |
| 스코프를 벗어날 때 `- Node A` 가 찍히는가 | 안 찍힌다. | 안 찍힌다. |  |
| **TODO 2 후** 찍히는가 | 찍힌다. | 찍힌다. |  |

- 왜 아무도 사라지지 않았는가 — 카운트가 0이 되지 못하는 과정을 한 줄로:
  스코프를 벗어나 지역 변수인 A, B는 제거되면서 Ref Count를 1씩 줄였지만 서로 살아 있기 때문에 Ref Count가 더 이상 줄지 않고 서로 붙들고 있다.
- `weak_ptr` 이 무엇을 하지 않기 때문에 순환이 끊기는가:
  weak_ptr은 접근은 하게 해주지만 Ref Count는 늘어나지 않는다.
- 게임 코드에서 이런 순환이 생기기 쉬운 자리 하나:
  액터와 컴포넌트 구조를 만약에 shared_ptr로 짰을 경우 구조상 액터는 컴포넌트를 가지고 있지만 만약 컴포넌트에서도 편의상 액터를 가지고 있다면 똑같은 문제가 발생할 수 있다.

## 한 문장 요약

> delete를 적었다고 객체가 꼭 해제되는 것은 아니다. **무엇이** 해제될지는 타입이(virtual 소멸자), **delete에 닿을지**는 실행 경로가(예외·return), **닿아도 지울지**는 참조 카운트가 정했다. 사람이 일일이 적다 보면 이 셋 중 어디선가 새기 때문에, 해제를 사람이 아니라 소멸자에 묶는 것이 RAII다. 실측에서 살아남은 Tracer가 6개에서 2개로 줄었다.
