## 어떻게 동작하나

- 생성 순서에서 기반과 멤버를 바꿨다고 가정하면 멤버에서 기반에 있는 멤버를 이용해 초기화하는 행동을 했을 때 기반보다 먼저 생성됐기 때문에 안 된다. 또, 멤버와 파생을 바꾸면 파생에서 생성자에서 자기 자신 멤버를 이용한 초기화 행동 등이 안 되기 때문에 기반 -> 멤버 -> 파생의 순서이다.
- 생성 순서 이유와 마찬가지로 소멸자를 호출했을 때 소멸자 안에 기반 또는 멤버가 먼저 없어져 있으면 안 되기 때문에.
- 소멸자 호출 시점에 vptr이 자신의 클래스 것으로 교체가 되기 때문에 소멸자 안에서 가상 함수를 부르면 항상 자기 자신 클래스의 함수 정의가 호출되게 된다.
- 업캐스팅한 포인터로 delete를 하는 경우에는 가상 소멸자가 필요하다.
- RAII는 한 스코프 내에 생성과 소멸을 보장하는 구조이다. 수동 delete를 사용하는 경우 함수 내에서 갑자기 다른 예외 처리가 발생하거나 return으로 함수를 빠져나갈 때 delete 호출을 실패해 메모리 누수를 발생시키는데 RAII는 자원의 수명을 다른 지역 변수에 위임시켜 스코프의 수명과 동일시해 소멸자를 호출하는 방식이다.
- unique_ptr은 객체의 소유를 하나밖에 인정하지 않지만 shared_ptr은 객체의 소유를 레퍼런스 카운트를 통해 여러 변수에서 소유할 수 있는 방식이다. 레퍼런스 카운트가 0이 되면 객체를 제거하는 방식이다.
- shared_ptr의 객체가 서로 참조하고 있는 경우 레퍼런스 카운터가 1에서 더 이상 떨어지지 못하기 때문에 제거되지 못한다.

## ⚠️ 틀렸던 것

- **`virtual` 소멸자가 필요한 조건** — 파생 클래스에 멤버 변수와 소멸자가 있거나, 업캐스팅을 하면 필요한 줄 알았다.
  실제로는 **업캐스팅한 포인터로 `delete` 를 할 때** 필요했다. (`Base` 에 `virtual` 이 하나도 없는 상태에서 잰 것)

  | 코드 | 결과 |
  |---|---|
  | `Base* b = &c; b->Use();` — 업캐스팅해서 사용만 | 정상 |
  | `Child* p = new Child; delete p;` — 파생 타입으로 `delete` | 정상 |
  | `Base* p = new Child; delete p;` — 업캐스팅해서 `delete` | **메모리 누수** |

- **생성 순서** — 기반 → 파생 → 멤버로 예측했다. 실제는 **기반 → 멤버 → 파생** 순이었다.
  파생 생성자 본문이 자기 멤버를 쓰기 때문에 멤버가 먼저 생성되어야 한다.
  실측은 `+ Vehicle` → `+ Engine` → `+ Car` 였고, 소멸은 역순이었다.

- **`virtual` 이 없을 때 멤버까지 안 없어진다** — 파생 소멸자가 안 불리는 것은 예측했는데, 멤버까지 없어지지 않는 것은 몰랐다.
  멤버 소멸은 **파생 소멸자의 뒷정리**라서, 파생 소멸자가 호출이 안 되면 멤버도 같이 남는다.
  `NoVirtualChild 가 쥔 자원` 이 그대로 샜다.

- **`sizeof(std::shared_ptr)`** — 8로 예측했는데 실제로 **16**이었다. 스마트 포인터는 크기가 다 포인터 하나 크기로 잘못 알고 있었다.
  `unique_ptr` 은 삭제자가 비어 EBO 로 0바이트가 되므로 8바이트지만,
  `shared_ptr` 은 객체 포인터 외에 제어 블록 포인터를 하나 더 들기 때문에 16바이트다.

- **`throw` 가 예외 메시지를 출력할 줄 알았다** — 실제로는 `catch` 에서 `e.what()` 으로 꺼내서 출력해야 된다.

## 언리얼과의 연결

- `UPROPERTY()` 로 리플렉션 시스템에 등록된 `UObject` 상속 객체들은 GC 가 수명을 관리한다. Mark & Sweep 방식의 GC 는 RootSet 에서 도달 가능한 객체들을 조사해 Mark 하고, Mark 되지 않은 객체들을 일정 주기마다 한꺼번에 정리한다.
- **다르다.** `Destroy()` 호출은 컴포넌트 등록을 해제하고 오브젝트 상태를 Garbage 로 표시한다. Mark 와 Sweep 단계는 GC 내부 동작이 결정한다.
- `TWeakObjectPtr` 은 대상을 살려두지 않는 약 참조라서 대상이 먼저 수거될 수 있다. 그래서 주소 대신 `InternalIndex` 와 `SerialNumber` 를 들고 있다가, 쓰기 전에 비교해서 살아 있는지 검사한다. 이 검사가 댕글링을 막는다.
- `TSharedPtr` 과 `TSharedRef` 는 내부 코드를 본 바로는 nullptr 을 담을 수 있는지 없는지 차이만 알 수 있었다.
